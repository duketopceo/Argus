# argus-reviewer eval — 2026-11-14 (phases: cold, cached replay, drift heal)

Suite: `evals/demo-suite` (7 tasks on `evals/demo-app`, a small shop page served on loopback)
Harness: `evals/run-phases.mjs` · Raw results: `evals/results/2026-11-14-phases.json`, `…-07b.json`, `…-escalation.json` · Folded numbers: `evals/results/2026-11-14-summary.json` (`node evals/summarize-phases.mjs`)
Spend: about $1.43 against a $3.00 hard cap, all through one OpenRouter key passed by environment only

The 2026-09-30 eval had three tasks, one run each, two models, and no drift. This one asks the question the product claim depends on: does a recording replay for free, and does it heal when the UI changes?

**Result in one paragraph.** Argus is as reliable as the vision model that grounds its steps. With `anthropic/claude-haiku-4.5` every one of 140 task-runs passed (35 per phase), cached replay made zero model calls and cost $0, and healing worked in 30 of 30 drifted task-runs. With `google/gemini-2.5-flash`, cold grounding passed 25 of 35, and after the UI changed only 16 of 30 task-runs that healed went on to pass. The three cheaper models are not usable as the grounding model on this suite: `gemini-2.5-flash-lite` passes 5 of 35 cold, `qwen3-vl-235b` 5 of 35, and `gpt-4.1-mini` cannot make a grounding call at all (HTTP 400 on every one). The replay mechanism itself held in every case where a recording existed. The weak phase is heal on cheaper models.

## Design

Each task is a td-API test file (find, click, type, assert), run in four phases against one workspace per model and replicate:

| Phase     | Cache | UI served   | What should happen                                  |
| --------- | ----- | ----------- | --------------------------------------------------- |
| cold      | empty | recorded UI | the model grounds every step                        |
| warm      | kept  | recorded UI | cache hit, no model call, $0                        |
| drift     | kept  | drifted UI  | fingerprint mismatch, the model re-grounds ("heal") |
| warm-heal | kept  | drifted UI  | cache hit on the healed entries, $0                 |

The drifted UI keeps every label and id. It changes colours, fonts and radii, adds a promo banner, and reorders the four panels, so every saved box moves. See `evals/demo-app/index.html` and `drifted.html`.

| Task                     | Covers                                     |
| ------------------------ | ------------------------------------------ |
| `01-click-add`           | click, assert on resulting state           |
| `02-form-newsletter`     | click input, type, click button, assert    |
| `03-form-shipping`       | two inputs, button, assert (5 steps)       |
| `04-multistep-checkout`  | add to cart, checkbox, place order, assert |
| `05-toggle-theme`        | click a toggle, assert                     |
| `06-assert-only`         | three assertions, no clicks                |
| `07b-empty-cart-message` | click, assert on a refusal message         |

5 replicates per model, 7 tasks, 4 phases: 140 task-runs per model, 700 in the headline set. Every task-run is recorded, pass or fail, with nothing retried or filtered (`evals/run-phases.mjs` appends each row as it finishes).

Models, all through OpenRouter, each as its own escalation target (`escalation_model` = the model under test) so a result belongs to one model. Argus's default escalates a failed grounding to `moonshotai/kimi-k2.5`; that configuration is measured separately below.

## Pass rate by phase

Task-runs passed out of 35 (7 tasks x 5 replicates).

| Model                              | cold  | cached replay | drift (heal) | replay after heal |
| ---------------------------------- | ----- | ------------- | ------------ | ----------------- |
| `anthropic/claude-haiku-4.5`       | 35/35 | 35/35         | 35/35        | 35/35             |
| `google/gemini-2.5-flash`          | 25/35 | 32/35         | 21/35        | 23/35             |
| `google/gemini-2.5-flash-lite`     | 5/35  | 6/35          | 14/35        | 14/35             |
| `qwen/qwen3-vl-235b-a22b-instruct` | 5/35  | 5/35          | 5/35         | 5/35              |
| `openai/gpt-4.1-mini`              | 5/35  | 5/35          | 5/35         | 5/35              |

Read these with two cautions. First, the 5/35 floor for three models is task 06, which makes no clicks (the model only judges text from the accessibility tree); every model passes it. Second, a task that fails cold has no recording, so in the later phases it grounds again from scratch. That is why `gemini-2.5-flash` shows 32/35 on replay but 25/35 cold, and why `gemini-2.5-flash-lite` improves on the drifted page (its cold grounding of the toggle button never works on the original layout and works every time on the drifted one). The conditional rows below remove that effect.

### Conditional rates (what the claim actually needs)

| Model                              | replay passes, given a cold pass | of those, zero model calls | task-runs where a heal fired, then passed | heal steps accepted | replay after heal passes, given a drift pass (zero calls) |
| ---------------------------------- | -------------------------------- | -------------------------- | ----------------------------------------- | ------------------- | --------------------------------------------------------- |
| `anthropic/claude-haiku-4.5`       | 35/35                            | 35/35                      | 30/30                                     | 55/55               | 35/35 (35/35)                                             |
| `google/gemini-2.5-flash`          | 25/25                            | 25/25                      | 16/30                                     | 52/52               | 21/21 (21/21)                                             |
| `google/gemini-2.5-flash-lite`     | 5/5                              | 5/5                        | 6/13                                      | 17/17               | 14/14 (13/14)                                             |
| `qwen/qwen3-vl-235b-a22b-instruct` | 5/5                              | 5/5                        | 0/0                                       | 0/0                 | 5/5 (5/5)                                                 |
| `openai/gpt-4.1-mini`              | 5/5                              | 5/5                        | 0/0                                       | 0/0                 | 5/5 (5/5)                                                 |

Cached replay never failed when a good recording existed: 100% pass and zero model calls in every model's eligible runs (the single exception in the last column is one `flash-lite` replay that re-grounded). The heal columns separate two things. A heal step is accepted when the model's new click point resolves to an element whose label matches the instruction; that happened in 100% of heals for every model. A task-run passes only if the action also took effect. For `gemini-2.5-flash`, 22 of its 52 accepted heal steps sat in task-runs that passed and 30 in task-runs that failed: 13 of the 14 failed task-runs failed on the assertion that followed the heal, 1 at a later step. Argus checks which element is under the point, not whether the click worked, so a wrong heal is caught only by the next assertion.

## Failure taxonomy

380 of the 700 headline task-runs failed. By kind, across all models and phases:

| Kind           | Count | What happens                                                                                                                                                               | Example (verbatim, trimmed)                                                                                         |
| -------------- | ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| wrong element  | 142   | The model's click point resolves to a different element than the instruction names. Argus rejects it and the step fails.                                                   | `td.find("the "Add to cart" button") failed: model grounded to "Gift wrap", which does not match the instruction`   |
| assert failed  | 92    | A step was accepted but the page state is not what the assertion expects, usually because the click did not take effect (after a heal, or a cold click on the wrong spot). | `assert("the page says the order is confirmed with 1 item, gift wrapped") failed: … it also shows "Gift wrap: off"` |
| API error      | 120   | `gpt-4.1-mini` only: OpenRouter returns HTTP 400 on every grounding call; assertion calls, which carry no JSON schema, work.                                               | `OpenRouter completion failed for all candidate models: OpenRouter request failed: 400`                             |
| no coordinates | 24    | The model answers `click` or `done` without x and y (`qwen3-vl`, once `flash-lite`).                                                                                       | `td.find("the "Email" input") failed: model returned "click" without coordinates`                                   |
| timeout        | 2     | A call exceeded the request timeout (`qwen3-vl`).                                                                                                                          | `OpenRouter completion failed for all candidate models: The operation was aborted due to timeout`                   |

The API error is a real incompatibility. OpenAI's strict structured outputs require every property in the action schema to be listed in `required`, and Argus's `action` schema leaves `x` optional: `Invalid schema for response_format 'action': 'required' is required to be supplied and to be an array including every key in properties. Missing 'x'.` No OpenAI model that enforces strict schemas can ground until the schema changes.

Failure patterns that look like model quality but are partly Argus behaviour:

- **A wrong heal is accepted.** After drift `gemini-2.5-flash` failed `02-form-newsletter` and `04-multistep-checkout` in 10 of 10 task-runs (04: all 5 on the assertion; 02: 4 on the assertion, 1 at the Subscribe step). The heal steps were accepted (the element under the point matched the label), but the Subscribe click or the Gift wrap toggle appears not to have taken effect: the assertion reports the email sitting in the box with no "Subscribed" message, or "Gift wrap: off".
- **Assertions lean on the screenshot.** In the drifted layout the Product panel's result lines sit near the bottom of the 1280 x 720 viewport. One `flash` failure says the matching text is in the accessibility tree "however, this text is not visible in the screenshot". The accessibility tree had the answer; the model chose the screenshot. `claude-haiku-4.5` trusts the tree and passes the same page.
- **A checkbox or text input grounds only through `aria-label`.** Argus matches the instruction against the element's `aria-label` or text content. A standard `<label for>` input has neither, so its snippet is empty and the step is rejected as `model grounded to ""`. This is independent of the model (see Deviations).

## What would fix it

| Weakness                                              | Evidence                                                                                                                                    | Fix                                                                                                                                                                                |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Heal accepted but the action did not work             | `flash` 16/30 healed task-runs pass, 52/52 heal steps accepted                                                                              | After a heal, verify the effect of the action (an a11y or region diff) before saving the new fingerprint; retry once with the next candidate point.                                |
| OpenAI models cannot ground                           | 120 of 120 `gpt-4.1-mini` task-runs that need a grounding call fail with HTTP 400                                                           | Make `x`, `y`, `text`, `keys`, `dx`, `dy`, `ms` required-but-nullable in the `action` schema (or send the schema non-strict for providers that reject it).                         |
| Label-based inputs never ground                       | pilot: `claude-haiku-4.5` failed all 3 label-dependent tasks in all 4 phases; by construction (the snippet is `aria-label` or text content) | Build the snippet from the accessible name (`el.labels`, `aria-labelledby`, `placeholder`) and not only `aria-label`/`textContent`.                                                |
| Cheaper models fail cold grounding                    | `flash-lite` 5/35, `qwen3-vl` 5/35 (no coordinates, wrong element)                                                                          | Document `claude-haiku-4.5` (or better) as the supported grounding model; keep cheap models for `assert` only; raise a clear error when a model fails the first N grounding calls. |
| Assertion prefers the screenshot over the tree        | `flash` cites "not visible in the screenshot"                                                                                               | Tell the assert prompt that the accessibility tree is authoritative for text presence.                                                                                             |
| The repo's own `evals/suite` assertions are dead code | `td.assert` returns a result object, which is always truthy; the test fails through the session instead                                     | Use `await td.assert(...)` bare, or return a boolean.                                                                                                                              |

## Deviations, pilots and honest caveats

- **Task 07 was replaced.** The original `07-empty-cart-guard` asserted "the page says the cart is empty", which is already true on the untouched page ("Cart: 0 items"). It could pass without the click landing: `flash-lite` scored 5/5 cold on it while failing every other click task, and its replays then re-grounded in 4 of 5 runs (no usable recording) and passed only 2 of 5. All 100 task-runs of version 1 are kept in `2026-11-14-phases.json` (task `07-empty-cart-guard`) and excluded from the headline with `--exclude`; `07b-empty-cart-message` asserts text that exists only after the click, and was run with the same protocol (`…-phases-07b.json`). With version 1 included, `flash-lite` would read 10/35 cold instead of 5/35.
- **Pilot runs found three suite bugs, all fixed before the measured run, and are not in the data.** (1) Inputs labelled with `<label for>` could not ground (see above); the demo app now sets `aria-label` on each input and the checkbox, as the repo's own `tests/fixtures/index.html` does. A one-replicate, one-model pilot (`claude-haiku-4.5`) failed all 3 label-dependent tasks in all 4 phases. (2) A negative assertion cannot be expressed because a failing `td.assert` fails the test itself. (3) A stray server from a killed pilot served a stale page to one model and made one pilot phase meaningless; `run-phases.mjs` now checks that its own server answers. Pilot spend: about $0.27, plus up to a few cents from a pilot that was killed mid-run.
- **Models not in the table.** One-replicate pilots on tasks 01 and 05 showed `google/gemini-3.1-flash-lite` and `meta-llama/llama-4-maverick` at 0/2 in every phase. Not pursued; the pilot rows are not committed.
- **`n` is small.** 35 task-runs per cell, 5 replicates; the pass rates carry wide intervals (25/35 is 71%, 95% interval roughly 55 to 84%). The `claude-haiku-4.5` result is 140/140, which supports "reliable on this suite", not "never fails".
- **One app, one drift.** The demo app is deliberately simple and the drift is a restyle plus reorder; a drift that changes labels or removes the element would test something else (Argus should fail, not heal).
- **Cost is the provider's reported per-call price** (`usage.cost` on each response), summed by Argus's own ledger, not a bill reconciliation.

## Reproduce

```bash
npm ci && npm run build
orch node evals/run-phases.mjs \
  --models anthropic/claude-haiku-4.5,google/gemini-2.5-flash \
  --reps 5 --cap 3 --out evals/results/my-run
node evals/summarize-phases.mjs evals/results/my-run.json
```

`OPENROUTER_API_KEY` must be in the environment (`orch` here supplies it from the keyring). `--escalation <model>` measures a named escalation model; the default (`self`) isolates one model. Each run writes `<out>.jsonl` as rows finish, then `<out>.json`. Workspaces and per-phase cache snapshots land in `evals/work/` (git-ignored).
